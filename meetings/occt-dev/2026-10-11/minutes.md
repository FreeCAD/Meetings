### Debugging and limitations of fillet and chamfer operations

GeeBee asked about visualizing intermediate steps in fillet operations to debug failures, particularly when selecting partial edges. Dmitrii explained that the current OpenCascade architecture, written decades ago, does not support intermediate values for these operations; shapes are only composed at the final step. Consequently, visualizing intermediate states is technically impossible with the current design. The conversation touched on the idea of recreating these operations from scratch using a geometry-only foundation, which is part of the new B-Rep graph work.

### OpenCascade 8.02 release status

Dmitrii provided an update on the upcoming 8.02 release. He stated that while many fixes for fillets and solvers are ready, the release will be delayed and contain fewer fixes than originally planned (around 10–15 instead of 30) due to breaking API changes and header modifications that prevent binary compatibility. He aims to merge his pending changes and release both development and maintenance branches soon.

### B-spline performance and memory constraints

The group discussed performance issues with B-splines containing many poles, such as those imported from airfoil files. Dmitrii explained that OpenCascade has hard-coded limits on knots and that increasing performance via caching significantly increases memory consumption (up to 20x), which is problematic for clients stuck on 32-bit systems or legacy proprietary dependencies. A proposal to add a configurable global cache for B-splines was mentioned as a pending experiment.

### 32-bit vs 64-bit architecture support

Dmitrii explained why OpenCascade continues to support 32-bit builds, citing client dependencies on legacy proprietary libraries that cannot be migrated. He also noted that for WebAssembly (WASM) targets, 32-bit builds can offer better performance (approx. 30% faster) due to smaller pointer sizes improving cache efficiency in browser sandboxes. Pieter remarked that FreeCAD, being open source, is not constrained by such legacy dependencies and has moved beyond 32-bit support.

### Topological naming and the B-Rep graph

The discussion turned to topological naming instability in FreeCAD, which Dmitrii attributed to limitations in the underlying OpenCascade 'TopoDS_Shape' architecture. He detailed his work on a new 'B-Rep graph' system, which stores topology, geometry, cache, layers, and supplemental storage in a unified, persistent structure. This new system offers robust topological naming, better memory efficiency, and faster operations like feature recognition and HLR. Unlike the current shape-based approach, the graph maintains relationships and attributes persistently through modifications.

### Forms workbench and subdivision modeling

GeeBee raised questions about the Forms workbench (subdivision modeling) in FreeCAD, noting it is slow and prone to freezing because it is implemented in Python. Dmitrii agreed that while the initiative is good for organic design and 3D printing, the implementation should ideally be in C++ for performance. He compared it to OpenCascade's own C++-based subdivision tools which are significantly faster.

### Upcoming OpenCascade applications and plugin system

Dmitrii announced plans to release new applications based on the B-Rep graph, including a web-based viewer called 'CascadeScope' and a main desktop application to replace CADA, available in community and business editions. He offered access to these tools for testing. The meeting concluded with a note that the discussion on the StepXML plugin system was deferred to the next meeting with Chris Hannes.
